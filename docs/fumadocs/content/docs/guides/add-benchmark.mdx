---
title: Add a benchmark
description: How to land a WorldFoundry benchmark — catalog, task contract, runner, and the evidence that separates integration from a leaderboard claim.
---

A WorldFoundry benchmark integration has four parts. The catalog records identity, provenance, and what the protocol actually measures. An external task manifest declares how samples become `GenerationRequest` rows. A runner or normalizer writes a scorecard shape the rest of the system can review. The readiness flags that `wf zoo benchmarks` shows come straight from catalog fields, so those fields must point at executed evidence. None of those pieces is a substitute for the others, and none of them, by itself, is a leaderboard claim.

The public surface for this work is Benchmark Zoo: catalog files under `worldfoundry/data/benchmarks/catalog/`, task files under `worldfoundry/data/benchmarks/tasks/external/`, and execution code under `worldfoundry/evals/tasks`. Use that path when you are tracking an external or community benchmark that has an official source, a dataset or prompt suite, a runner, and runtime stages. Per-benchmark pages live on [Benchmark Hub](/docs/evaluation/benchmark-hub). Reusable scorers that are not protocol-specific live under [Metrics](/docs/evaluation/metrics). Embodied simulators have extra asset and Docker steps in [Embodied official runtime](/docs/evaluation/embodied-official-runtime). The model side of the same artifact boundary is [Add a model](/docs/guides/add-model).

## Keep the first PR narrow

The first pull request should prove one support surface end to end. Pick one benchmark id, one catalog YAML, one external task contract, one callable runner or official-result normalizer, and one report that a reviewer can open without guessing your machine. That is enough to show catalog → task → runner → scorecard artifacts works for assets the user supplies.

Do not wait until every official dimension, every judge weight, and every leaderboard split is green. A bounded official-validation import that writes an honest scorecard is a better first PR than a wide metadata dump that also claims `leaderboard_valid: true`. Do not rewrite shared metric APIs or invent a second catalog parser in the same change.

## What an integration actually touches

A WorldFoundry benchmark is a stack of contracts, not a single script. Identity lives in `worldfoundry/data/benchmarks/catalog/<family>/<benchmark-id>.yaml`: `id`, aliases, family, modalities, and the normalized tasks the rest of the zoo will search. Source provenance lives next to it — official repository, paper, project page, license, clone target, and whatever access note a later runner will need. If the GitHub URL is unverified, say so. Never record a guess as verified.

The dataset block is about access, not about copying videos into git. Record dataset ids, whether a Hugging Face mirror exists, what the cache expectation is, which filters apply, and any unsafe or gated flags. Some video benchmarks, such as VBench, do not need a public dataset at all: they consume a prompt suite plus generated videos from `WORLDFOUNDRY_GENERATED_ARTIFACT_DIR`. Embodied benchmarks usually need a data root, a simulator checkout, and sometimes a Docker image. Write the condition that is true, including `not_applicable` when that is the official shape.

The runner block names the callable surface: runner target, official validation mode, the official benchmark command if you wrap one, and the artifacts a successful run must leave behind. Metrics on the catalog are the protocol’s scores — ids, direction, aggregation, ranges, and leaderboard keys — not a second copy of the in-tree metric registry. If a dimension is only an approximation of the official script, say that on the Benchmark Hub page and in the catalog notes. Do not silently swap in CLIPScore because the official judge is heavy.

The `contract` block states the benchmark's external interface: the `input_keys` a run consumes, the `output_keys` it writes, `notes`, and `requires_upstream_runtime: false` when scoring needs no upstream package. Metric ids default to the catalog metrics; list `metric_ids` in the block only when the reported set differs. Catalog and task runner targets name the contract by benchmark id, as in `worldfoundry.evals.tasks.contracts.external:<benchmark-id>`.

Benchmarks that generate videos from their own prompt suite add a `generation` block: `request_provider` is the `module:function` that returns the generation requests, `artifact_materializer` is the optional `module:function` that copies generated videos into the official layout, `dataset_root_parameter` and `split_parameter` name the provider keywords that accept those overrides, and `missing_requests_hint` is shown when the prompt assets are absent.

The task contract sits in `worldfoundry/data/benchmarks/tasks/external/<benchmark-id>.yaml`. That file is how a prompt list or simulator episode becomes `GenerationRequest` rows. Keep protocol-specific mapping there, or in the runner that reads it. Do not teach a model pipeline the VBench dimension list, and do not teach a metric how to launch Cosmos.

Evidence fields — check notes, report paths, blockers, executed commands — are the catalog's pointers to proof, and readiness flags are computed from them without re-running anything. The proof itself is a file under `tmp/`, not a sentence in YAML.

## Integration is not a leaderboard

WorldFoundry splits framework integration from leaderboard eligibility on purpose. A runner that can import official-shaped results and write `scorecard.json` is integration evidence. A number that may be compared to a published table requires the official scorer or judge, the declared asset coverage, and a scorecard that still says the run is eligible.

That is why a catalog can be `integrated` and still carry `leaderboard_valid: false`, `official_benchmark_verified: false`, and, when you only normalize upstream files, `verification_status: normalizer_only` plus `normalizer_only: true`. VBench is the usual example: a bounded official GPU check on one dimension is real integration evidence; the full prompt suite and the remaining heavy dependencies are still pending, so the leaderboard flag stays false. Do not promote the flag because a single video scored.

If you only have a normalizer, you may still mark the surface `integrated` once the CLI command, the artifact and data requirements, and the normalization report exist. Leave the three leaderboard-limiting fields in place until the official scorer or judge has actually run.

## Write the manifests, then see if the zoo agrees

Draft the catalog YAML by responsibility, not as one unsorted table. Identity, source, dataset, runner, metrics, and evidence should be readable as separate stories. Add the matching external task file in the same PR so `tasks show` and `benchmark-show` cannot disagree about the id.

Then ask the zoo whether it parsed what you meant. From the unified environment:

```bash
wf zoo benchmarks --json
wf zoo benchmark-show --benchmark-id <benchmark-id> --include-spec --json
wf zoo benchmark-specs --benchmark-id <benchmark-id> --json
wf tasks show --task-type <benchmark-id> --json
```

`benchmark-show` is the fastest way to see aliases, required env vars, blockers, and the resolved spec. `benchmark-specs` is the compact view a runner will consume. `tasks show` confirms the external task contract registered under the same id. If these three disagree, fix the YAML before you touch a GPU.

## Prove the runner can write a scorecard

The first executable milestone is official validation, not a full leaderboard sweep. Import official-shaped results — or a small generated-artifact directory the protocol accepts — and write a reviewable scorecard:

```bash
wf zoo benchmark-run \
  --benchmark-id <benchmark-id> \
  --output-dir tmp/benchmark_zoo/official_validation/<benchmark-id> \
  --mode official-validation \
  --official-results-path <official_results.json> \
  --generated-artifact-dir <generated_artifacts> \
  --json
```

A passing import is development evidence. It shows the normalizer, artifact kinds, and scorecard writer agree. It does not show that your videos cover the official prompt list, that the judge weights were the published ones, or that the number is comparable to the paper. Those claims wait for the official command, the declared assets, and a scorecard that still records the gaps.

When metadata looks right, run the declared runtime profile so missing datasets, licenses, and conda prefixes show up as blockers in a report:

```bash
wf preflight runtime \
  --profile <benchmark-id> \
  --manifest worldfoundry/data/benchmarks/runtime_profiles/official/<benchmark-id>.yaml \
  --output-dir tmp/preflight/runtime/<benchmark-id> \
  --json
```

Add network, credential, or execute flags only on a machine that is allowed to fetch data and has the runtime capacity. Read the JSON report for blockers, stage status, and next action; the preflight also writes `preflight_report.json` in its output directory. Open logs only when a stage failed. Record the preflight report and the scorecard of the executed mode in the catalog evidence fields. When a manifest change alters what runs, rerun preflight and validation before keeping `integrated`.

Embodied benchmarks usually need one more hop after import. Roll out in the official simulator or Docker evaluator, write the result files those projects already emit, then import with `official-validation`. Do not invent a parallel score format inside WorldFoundry and call it official. Env vars and asset roots are listed in [Embodied official runtime](/docs/evaluation/embodied-official-runtime).

## Status has to match what the runner can prove

`planned` means the metadata exists but the declared runner, importer, normalizer, or artifact contract is not yet callable with evidence. Use it for a catalog row you are still wiring. `blocked` means a concrete official condition is missing: code, data, judge weights, license access, or a runtime dependency you cannot stage. Write the reason in `blockers` so the next person does not rediscover it. `integrated` means the declared WorldFoundry surface is callable and evidenced — an in-tree runner, an official command wrapper, an isolated importer, or an official-result normalizer can write the expected scorecard artifacts for user-supplied assets.

Promotion language is part of the contract. If the PR says `integrated` and the scorecard cannot be opened, the status is wrong. If the PR says the number is leaderboard-valid and `leaderboard_valid` is still false, the prose is wrong. Change both together, and only after the evidence was produced from the current manifests.

## What a reviewer needs in the PR

A reviewer should be able to walk from a catalog sentence to a command and an artifact without asking which node you used. Attach the catalog and task diffs — `worldfoundry/data/benchmarks/catalog/**/<benchmark-id>.yaml`, `worldfoundry/data/benchmarks/tasks/external/<benchmark-id>.yaml`, and any runner or normalizer files — plus the metadata-check output from `benchmark-show` / `benchmark-specs` / `tasks show`. Attach the preflight report, the scorecard from the executed mode, the dataset cache path and access condition without the data itself, raw logs, and expected artifact paths. If a stage was skipped, write the license, API, dataset, or hardware reason in the catalog `blockers`, not only in the PR body.

Do not commit datasets, generated videos, judge checkpoints, API keys, or private simulator images. Reference them by path and hash in the catalog evidence and the PR. When you promote status, rerun the preflight and `wf zoo benchmark-show` so the catalog, the readiness flags, and the PR tell the same story.
