---
title: 添加 Benchmark
description: 如何把一个 benchmark 接到 WorldFoundry：catalog、task 契约、runner，以及把「已接入」和「可上榜」分开的证据。
---

WorldFoundry 的 benchmark 集成由四部分组成。Catalog 记录身份、出处，以及协议到底测什么；external task manifest 声明样本如何变成 `GenerationRequest`；runner 或 normalizer 写出系统其余部分能审查的 scorecard；`wf zoo benchmarks` 显示的 readiness 标志直接由 catalog 字段计算，所以这些字段必须指向实际执行过的证据。这几层互相替代不了，单独任何一层也不等于 leaderboard 声明。

当前公开 surface 是 Benchmark Zoo：catalog 在 `worldfoundry/data/benchmarks/catalog/`，task 在 `worldfoundry/data/benchmarks/tasks/external/`，执行代码在 `worldfoundry/evals/tasks`。需要追踪带有官方源码、数据集或 prompt suite、runner 和 runtime stages 的外部/社区 benchmark 时，应使用这条集成路径。每个 benchmark 的页面在 [Benchmark Hub](/zh/docs/evaluation/benchmark-hub)；与协议无关的可复用 scorer 在 [指标](/zh/docs/evaluation/metrics)；具身 simulator 的资产和 Docker 步骤在 [Embodied 官方运行准备](/zh/docs/evaluation/embodied-official-runtime)。同一条 artifact 边界的模型侧见 [添加模型](/zh/docs/guides/add-model)。

## 第一份 PR 要窄

第一份 pull request 只需要证明一个 support surface 能端到端成立：一个 benchmark id、一份 catalog YAML、一份 external task 契约、一个可调用的 runner 或 official-result normalizer，以及一份 reviewer 不用猜机器也能打开的 report。这样就足以证明 catalog → task → runner → scorecard artifacts 能基于用户提供的资产正常运行。

不必等所有官方维度、所有 judge 权重、所有 leaderboard split 都通过后再合入。一次如实写出 scorecard 的 bounded official-validation，比一份仍宣称 `leaderboard_valid: true` 的大而全元数据更适合作为第一份 PR。同一次改动里不要重写公共 metric API，也不要再发明一套 catalog parser。

## 一次集成会改到哪里

WorldFoundry 里的 benchmark 是一叠契约，不是一个脚本。身份在 `worldfoundry/data/benchmarks/catalog/<family>/<benchmark-id>.yaml`：`id`、alias、family、modalities，以及 zoo 会检索的 normalized tasks。出处写在旁边——官方仓库、论文、项目页、license、clone target，以及后续 runner 需要的 access note。GitHub URL 未经核实就明确标注为未核实。不要把猜测记成已核实。

Dataset 一段讲的是访问条件，不是把视频拷进 git。记录 dataset id、有没有 Hugging Face 镜像、cache 期望、过滤条件，以及不安全或 gated 标记。有些视频 benchmark，例如 VBench，根本不需要公开数据集：它们消费 prompt suite，再加上 `WORLDFOUNDRY_GENERATED_ARTIFACT_DIR` 里的生成视频。具身 benchmark 通常需要 data root、simulator checkout，有时还要 Docker 镜像。把真实条件写清楚，官方形状就是「不适用」时用 `not_applicable`。

Runner 一段明确列出可调用的 surface：runner target、official validation mode、若包装了官方命令就写上命令，以及一次成功运行必须留下的产物。Catalog 上的 metrics 是协议自己的分数——id、方向、聚合、数值范围、leaderboard key——不是树内 metric registry 的第二份拷贝。如果某个维度只是官方脚本的近似，就应在 Benchmark Hub 页和 catalog notes 里写明。不要因为官方 judge 太重，就静默换成 CLIPScore。

`contract` 一段写明 benchmark 的对外接口：一次运行消费的 `input_keys`、写出的 `output_keys`、`notes`，打分不需要上游包时写 `requires_upstream_runtime: false`。Metric id 默认取 catalog 的 metrics；只有上报的集合不同时，才在这一段里列出 `metric_ids`。Catalog 和 task 的 runner target 按 benchmark id 指向契约，例如 `worldfoundry.evals.tasks.contracts.external:<benchmark-id>`。

用自带 prompt 集生成视频的 benchmark 再加一个 `generation` 块：`request_provider` 是返回生成请求的 `module:function`；`artifact_materializer` 可选，是把生成视频复制成官方目录结构的 `module:function`；`dataset_root_parameter` 和 `split_parameter` 写明 provider 接收这两种覆盖时用的关键字参数；`missing_requests_hint` 是 prompt 资产缺失时给出的提示。

Task 契约在 `worldfoundry/data/benchmarks/tasks/external/<benchmark-id>.yaml`。prompt 列表或 simulator episode 变成 `GenerationRequest`，靠的是这份文件。协议相关的映射留在这里，或留在读它的 runner 里。不要让模型 pipeline 去懂 VBench 的维度表，也不要让 metric 去启动 Cosmos。

Evidence 字段——check notes、report 路径、blockers、执行过的命令——是 catalog 里指向证据的句子，readiness 标志直接由它们计算，不会重新运行任何东西。证据本身是 `tmp/` 下的文件，不是 YAML 里的一句话。

## 接入不是上榜

WorldFoundry 刻意把框架接入和 leaderboard 资格分开。Runner 能导入官方形态的结果并写出 `scorecard.json`，这是 integration evidence。若要让数字可与论文表格比较，需要官方 scorer 或 judge、声明过的资产覆盖，以及一份仍然写明资格的 scorecard。

所以 catalog 可以是 `integrated`，同时带着 `leaderboard_valid: false`、`official_benchmark_verified: false`；若你只做了归一化，还要保留 `verification_status: normalizer_only` 和 `normalizer_only: true`。VBench 是常见例子：某一维上的 bounded official GPU 检查是真实的接入证据；完整 prompt suite 和其余重依赖仍未完成，leaderboard 标志就必须为假。不要仅因一条视频得出分数就将标志改为真。

如果手里只有 normalizer，只要 CLI 命令、artifact / 数据要求和 normalization report 都在，仍然可以把 surface 标成 `integrated`。那三个限制上榜的字段，在官方 scorer 或 judge 真正跑过之前不要动。

## 先写 manifest，再问 zoo 同不同意

Catalog YAML 按职责起草，不要堆成一张无序大表。Identity、source、dataset、runner、metrics、evidence 应能当成几段分开的故事来读。同一份 PR 里补上对应的 external task，避免 `tasks show` 和 `benchmark-show` 对同一个 id 说法不一致。

然后检查 zoo 的解析结果是否符合预期。在 unified 环境里：

```bash
wf zoo benchmarks --json
wf zoo benchmark-show --benchmark-id <benchmark-id> --include-spec --json
wf zoo benchmark-specs --benchmark-id <benchmark-id> --json
wf tasks show --task-type <benchmark-id> --json
```

`benchmark-show` 最快能看到 alias、必需环境变量、blockers 和解析后的 spec。`benchmark-specs` 是 runner 会消费的压缩视图。`tasks show` 确认 external task 契约挂在同一个 id 下。如果这三处结果不一致，先修正 YAML，再执行 GPU 任务。

## 证明 runner 能写出 scorecard

第一个可执行里程碑是 official validation，不是完整 leaderboard 扫表。导入官方形态的结果——或协议接受的一小份生成资产目录——写出可审查的 scorecard：

```bash
wf zoo benchmark-run \
  --benchmark-id <benchmark-id> \
  --output-dir tmp/benchmark_zoo/official_validation/<benchmark-id> \
  --mode official-validation \
  --official-results-path <official_results.json> \
  --generated-artifact-dir <generated_artifacts> \
  --json
```

Import 通过，只是开发证据。它说明 normalizer、artifact 种类和 scorecard 写出是对齐的。它不说明你的视频覆盖了官方 prompt 列表、judge 权重是论文用的那份，或这个数字可以和论文比。这些声明需要等待官方命令运行完成，并以已声明的资产和仍明确记录缺口的 scorecard 为证。

Metadata 看起来对了之后，跑声明的 runtime profile，让缺数据集、license、conda prefix 以 blocker 的形式出现在 report 里：

```bash
wf preflight runtime \
  --profile <benchmark-id> \
  --manifest worldfoundry/data/benchmarks/runtime_profiles/official/<benchmark-id>.yaml \
  --output-dir tmp/preflight/runtime/<benchmark-id> \
  --json
```

只有机器被允许拉数据、并且有 runtime 容量时，才加网络、凭证或 execute 类 flags。先读 JSON report 看 blockers、stage 状态和下一步；preflight 还会在输出目录写出 `preflight_report.json`。stage 失败后再查看 log。把 preflight report 和实际执行模式的 scorecard 记录到 catalog 的 evidence 字段。manifest 的改动影响实际运行内容时，先重跑 preflight 和验证，再保留 `integrated`。

具身 benchmark 在 import 之后通常还需要一个额外步骤。在官方 simulator 或 Docker evaluator 里 rollout，写出那些项目已经在用的 result 文件，再用 `official-validation` 导入。不要在 WorldFoundry 里另造一套分数格式还称之为 official。环境变量和资产根目录见 [Embodied 官方运行准备](/zh/docs/evaluation/embodied-official-runtime)。

## 状态必须和 runner 能证明的一致

`planned` 表示元数据在，但声明的 runner、importer、normalizer 或 artifact 契约还不能带着证据被调用。仍在接入的 catalog 条目应使用此状态。`blocked` 表示有具体的官方条件缺失：代码、数据、judge 权重、license 或你落不了盘的 runtime 依赖。把原因写进 `blockers`，便于后续维护者排查。`integrated` 表示声明的 WorldFoundry surface 可调用且有证据——仓内 runner、官方命令包装、隔离 importer，或 official-result normalizer，能针对用户提供的资产写出预期的 scorecard。

Promotion 用语也是契约的一部分。PR 写 `integrated` 却打不开 scorecard，状态就错了。PR 说数字可上榜、YAML 里 `leaderboard_valid` 仍是 false，正文就错了。两处应同步修改，且只能在基于当前 manifest 生成证据后修改。

## PR 里 reviewer 需要看到什么

Reviewer 应能从 catalog 里的一句话走到一条命令和一份产物，而不必问你用了哪台机器。附上 catalog 与 task 的 diff——`worldfoundry/data/benchmarks/catalog/**/<benchmark-id>.yaml`、`worldfoundry/data/benchmarks/tasks/external/<benchmark-id>.yaml`，以及 runner / normalizer 文件——再加上 `benchmark-show` / `benchmark-specs` / `tasks show` 的元数据检查输出。附上 preflight report、实际执行模式的 scorecard、数据集 cache 路径和访问条件（不要数据本身）、raw log 和预期产物路径。若某 stage 跳过了，把 license、API、数据集或硬件原因写进 catalog 的 `blockers`，不要只写在 PR 正文。

不要提交数据集、生成视频、judge checkpoint、API key 或私有 simulator 镜像。在 catalog evidence 和 PR 中用路径和哈希引用它们。提升状态时重跑 preflight 和 `wf zoo benchmark-show`，确保 catalog、readiness 标志和 PR 的表述一致。
