WorldFoundry is open-source infrastructure for world intelligence. It is not a new model architecture. Discovery, runtime and asset preparation, inference, artifact inspection, and benchmark evidence share one workflow across video, 3D/4D, embodied action, and interactive worlds.

A generative world model is more than a perceptual generator. It maintains persistent, history-conditioned state, updates that state under actions or interventions, and produces temporally coherent trajectories. Visual plausibility is not sufficient evidence. The operational definition and capability progression are in [World models](/docs/overview/world-models).

The current release integrates 270 models and nearly 100 benchmark and metric implementations. Catalog inclusion is not a runnable runtime. A demo is not benchmark evidence. An ingested score is not official leaderboard parity. Those states stay separate, with provenance.

WorldFoundry is most useful when work spans **more than one model, benchmark, or execution surface**. The technical report calls this *commensurability without homogenization*: heterogeneous systems stay inspectable under shared operational and evidential contracts, without being forced into a single representation, task, or metric.

That is why the shared workflow exists:

- **One operational vocabulary.** Stable model and benchmark IDs, plus request, result, artifact, manifest, and scorecard records, replace repository nicknames and handwritten paths. You can ask whether a model was only cataloged or actually executed, which checkpoint and runtime ran, whether samples were covered, and whether a score was normalized, officially computed, or validated for a leaderboard.
- **Shared glue.** Environment bootstrap, checkpoint lookup, input shaping, output naming, job records, previews, and metric aggregation stay shared. Model-specific code lives in pipelines and operators; benchmark-specific code stays in runners and metrics.
- **Reusable artifacts.** Generated output is not trapped in a UI session. The same artifacts can be inspected, rescored, converted, compared, or audited later without loading the model again.
- **Evidence beyond a command.** The same command can change meaning after a checkpoint, package, dataset, or evaluator changes. Ledgers, identities, blockers, and scorecards record both what ran and what the result is allowed to claim.
- **Multiple interfaces, one backend.** TUI, CLI, Studio, Python, and MCP reuse the same catalogs and contracts. The interface can change; the run identity and durable outputs do not.

This fits teams that maintain or compare several world-model families, separate generation from evaluation, reuse expensive artifacts, or need stable machine-readable discovery for people and agents. The more models, benchmarks, machines, and reviewers you have, the more those contracts repay their setup cost.

## A first run

For `matrix-game-2`, confirm the catalog entry and local checkpoint, then generate one small result:

```bash
bash scripts/inference/prepare_model_infer.sh matrix-game-2 --download
python -m worldfoundry.evaluation zoo model-download \
  --model-id matrix-game-2 --check-local --json

bash scripts/inference/test_nav_video_gen.sh matrix-game-2 \
  --output-dir tmp/matrix_game2_first_run
```

That run justifies one claim: this configuration produced an inspectable artifact. It does not mean a benchmark completed. Layers and contracts are in [Design](/docs/overview/design); the concrete inventory is in [What's included](/docs/overview/capabilities).
