Native-diffusion families and their **consolidation status**: which canonical roles each model reuses, the local structural/checkpoint validation behind each recipe, and which CUDA artifact parity is still open. For the sampling kernel, component boundaries, dependency rules, and the migration *process*, read [Native diffusion](/docs/maintainers/architecture/native-diffusion); for the shared primitives these families depend on, read [Core infrastructure](/docs/maintainers/architecture/core-infrastructure).

<Callout type="info">
  A recurring distinction below: **structural/checkpoint validation** (exact key or tensor coverage against a released checkpoint) is not the same as **CUDA artifact parity** (a real GPU run producing matching output). CUDA parity is a separate release gate per family and is not implied by structural validation.
</Callout>

## Scheduler and component consolidation

Wan's shifted trajectory is canonical, and the flow UniPC/DPM++ implementations live once under `schedulers/`. Both Wan and Cosmos compatibility paths resolve to the same native UniPC class; Wan's six DPM++ and six UniPC entry points are one-way exports. Validation covered schedule construction, noise interpolation, flow conversion, and complete multistep trajectories. FLUX.2's latent autoencoder lives under `models/autoencoders/flux2`, uses the shared core-backed module loader, and its benchmark caller uses the canonical path.

## Sana

Sana image, video, streaming, ControlNet, and SANA-WM variants share the same role-based package as every other diffusion family. Checkpoint-shaped network math lives under `models/networks/sana`, DC-AE under `models/autoencoders/sana`, conditioning under `models/encoders/sana`, and construction under recipes and schedulers. Its Wan VAE variants use framework-independent adapters rather than Diffusers mixins. Shape, volume, configuration-filtering, state-dict-prefix, and Triton autotune helpers come from `worldfoundry/core`.

## Wan family

`wan2.1-t2v-1.3b` is the reference built-in native recipe. Its UMT5 conditioner, tokenizer resource, DiT, latent initializer, shifted Euler scheduler, and VAE decoder are assembled through the standard strategy. The checkpoint resolver first asks `worldfoundry/core` for a staged local Hub snapshot, then uses filtered Hub materialization; the repository revision and required files remain declarative. Local checkpoint validation confirms exact key coverage for DiT (825), text encoder (242), and VAE (194). CUDA artifact parity for this recipe remains a separate release gate.

Wan-derived products use the same roles instead of carrying private Wan frameworks. PUSA, SAMA, Spatia, MultiWorld, FantasyWorld, and WoW compose the canonical Wan transformer, conditioning, codec, checkpoint loading, LoRA/control helpers, and staged runner with only their checkpoint-visible differences retained. Exact local graph checks cover MultiWorld (984/984 tensors), FantasyWorld's Wan2.1 overlay (3,132/3,132) and both Wan2.2 high/low branches (2,658/2,658 each), and WoW 1.3B (825/825). The WoW graph is inferred from the released transformer checkpoint and correctly selects VAE-only first-frame conditioning. WoW DiT 2B supplies its post-trained transformer checkpoint to the canonical Cosmos Predict2 route without its own scheduler, tokenizer, or pipeline. Its checkpoint graph and CUDA artifact parity remain pending because the pinned Hub snapshot does not contain the expected `wow_dit_2b.pt` asset. CUDA artifact parity for these Wan-derived products is still open.

## Matrix Game 3.5

`matrix-game-3.5-first-person` and `matrix-game-3.5-third-person` are separate frozen recipes in the same default registry, each bound directly to its released full 829-key DiT checkpoint. Exact header-to-model validation fixes the first-person subject-reference embedding capacity at two and the third-person capacity at four; the product profile still limits a third-person request to two references. They reuse the canonical Wan UMT5 conditioner, 48-channel Wan2.2 VAE, latent initializer, scheduler, core attention, loader, and standard runner. Structural validation also matches all 242 text-encoder keys and all 196 converted Wan2.2 VAE keys. Mosaic, PRoPE, and subject-memory tensor computation lives in the Matrix denoiser component; the synthesis route submits a `DiffusionRequest` to `NativeDiffusionPipeline`. Runtime configuration exposes inference-native names only. CUDA artifact parity for the native recipes is still open.

## Echo Memory

Echo Memory contributes eleven immutable model recipes to the same default registry. Each public model ID fixes its checkpoint file and memory architecture; none is an option on a shared mutable Echo pipeline. The denoiser promotes the canonical Wan blocks with checkpoint-compatible Echo modules, while conditioner, VAE, core loading, UniPC scheduler, runner, and runtime policy remain shared infrastructure. The framework-owned `frozen-context` strategy initializes target noise with a clean context suffix, relocks that suffix after every solver step, and decodes target latents only. Exact native model coverage was checked for all 1,185 tensors in the released K=1 checkpoint. Native CUDA artifact parity is still open.

## LTX

`ltx-2-i2v`, `ltx-2.3-i2v`, and `ltx-video-i2v` are independent recipes using the same `NativeDiffusionPipeline`, core-backed loader, runtime policy, and framework-owned `joint-multistage` runner. LTX-2.x couples video and audio across low-resolution generation and spatial-refinement stages; LTX-Video 0.9.8 uses the same runner with a video-only modality across two stages, with its spatial upsampler applied between them. Transformers supplies only checkpoint-compatible Gemma/T5 architectures, not an inference backend. Exact local checkpoint coverage was verified for every role: LTX-2 transformer 3,510, connector 59, video encoder/decoder 94/92, audio decoder 58, vocoder 194, upsampler 73, statistics 2, and Gemma 1,066; LTX-2.3 transformer 4,186, connector 262, video encoder/decoder 86/86, audio decoder 58, vocoder 1,227, upsampler 72, statistics 2, and Gemma 1,066; LTX-Video transformer 1,215, video encoder/decoder 94/134, and T5 220. CUDA artifact parity remains a separate release gate.

## Cosmos Predict 2.5 / Transfer 2.5

Cosmos Predict 2.5 and Transfer 2.5 follow the same rule. The 2B and 14B Predict recipes and the 2B controlled-video Transfer recipe share one native runner, Reason1 conditioner, Wan codec instance, Karras flow-UniPC scheduler, core loader, and offload policy. Transfer contributes a checkpoint-shaped VACE network branch—four control blocks at base layers 0/7/14/21 and an eight-modality control embedder—but no ControlNet backend or family runner. The released Predict and Transfer configs keep temporal FPS RoPE modulation disabled. Exact local structure checks cover Predict 2B (569 transformer tensors), Predict 14B (729), Reason1 language weights (338), and the Wan codec (194); the native Transfer control path also passes a finite tiny forward. Transfer checkpoint structure and full native CUDA artifact parity remain pending because the exact general/edge asset was unavailable locally.

## Cosmos Predict1 / Predict2 (GEN3C)

Cosmos Predict1 and Predict2 use the same architecture. `gen3c-cosmos1-7b` binds a 570-tensor native DiT, the shared T5-11B conditioner, the Cosmos Tokenize1 codec, Karras x0 AB2, and a standard initializer. Its MoGe depth inference, named camera paths, and RGBD forward warp are model preprocessing backed by reusable `worldfoundry/core` geometry—not a GEN3C runner. `cosmos-predict2-2b-video2world` and `cosmos-predict2-14b-video2world` share the Predict2/2.5 backbone module and Wan codec, while recipe configuration selects 567/727-tensor topologies, T5-11B, sigma-max initialization, and Rectified Flow AB2. Both generations use the framework-owned terminal clean-prediction lifecycle rather than a family runner. Registry, tiny-forward, mask, geometry, and scheduler validation pass locally. Predict2 weights are gated and full native GPU artifact parity for both generations remains pending.

## HunyuanVideo

HunyuanVideo follows the same composition boundary. `hunyuanvideo-t2v`, `hunyuanvideo-i2v`, `hunyuanvideo-1.5-t2v`, and `hunyuanvideo-1.5-i2v` are four immutable recipes in the default registry and use the standard framework runner. Original and 1.5 releases own checkpoint-compatible denoisers, prompt conditioning, and latent codecs only; scheduling, loading, offload, execution, media IO, and public pipeline behavior remain shared. Their MLP, text/timestep projection, AdaLN/final layer, prefix modulation, attention, and RoPE helpers resolve to shared core primitives while retaining checkpoint-visible submodule names. Exact local checkpoint checks cover the converted original T2V DiT (856 source keys to 976 native keys), original I2V DiT (856 keys), original causal VAE (248 keys), 1.5 DiT (1,793 keys), 1.5 VAE (218 keys), and the I2V-only SigLIP vision encoder (448 keys), with no missing, unexpected, or shape-mismatched tensors. The gated FLUX.1-Redux-dev vision asset is an explicit I2V component dependency instead of an inferred sibling directory. The original causal 3D VAE is one native PyTorch module shared by encode and decode. All four recipes still need checkpoint-backed CUDA artifact parity. Hunyuan GameCraft and HunyuanWorld-Voyager use a synthesis-level compatibility layer rather than these native recipes.

## Self-Forcing and Causal-Forcing

`self-forcing` and the four Causal-Forcing students (`causal-forcing-chunkwise`, which the public `causal-forcing` ID resolves to, `causal-forcing-framewise`, `causal-forcing-framewise-1step` and `causal-forcing-framewise-2step`) are immutable recipes on the framework-owned `autoregressive-window` runner. They share one recipe builder: the causal Wan2.1 1.3B denoiser with a 21-latent-frame KV cache and distilled x0 prediction, the canonical Wan2.1 umT5 conditioner, the Wan flow-match scheduler on the shift-5 calendar, and the bf16 Wan2.1 codec. The releases differ only in the generator file, the latent block size, the fixed step lists (with a four-step first block for Causal Forcing++), and whether an image seeds the first latent frame. `NativeSelfForcingPipeline` and `NativeCausalForcingPipeline` are the public pipelines for both catalog bindings and Studio, and serve the same resident realtime session.

The vendored `self_forcing_runtime/` and the Causal-Forcing inference tree, their operators, synthesis facades and runtime configs are deleted; their branches in the shared subprocess bridge go when RollingForcing migrates. RollingForcing keeps the shared forcing bridge (`synthesis/visual_generation/forcing/runtime.py`, `shared/`) and the rolling-window inference pipeline it imports from `forcing/causal_forcing_runtime/long_video/` until it migrates. Accepted-reference parity is bitwise for every release: strict checkpoint loading, prompt embeddings, every generator call, the final rollout latents and the decode of the reference latents match recorded runs of the official inference scripts (`tests/manual/self_forcing_parity.py`), and the replay cases `self-forcing-t2v-short`, `causal-forcing-chunkwise-t2v-short` and `causal-forcing-framewise-short` cover the public route.

## LVDM

LVDM's checkpoint-shaped implementation is split by role:

- `models/networks/lvdm`: latent-diffusion orchestration, 3D UNets, and checkpoint-visible attention blocks;
- `models/autoencoders/lvdm`: the latent codec;
- `models/encoders/lvdm`: text, image, adapter, and resampler conditioning;
- `schedulers/lvdm`: DDIM variants, diffusion schedules, and the Vid2World KV cache;
- `core/configuration/factory.py` and `core/nn`: generic config construction, distributions, EMA, checkpoint, and classic convolution helpers.

Vid2World dataset adapters belong to its synthesis package under `synthesis/visual_generation/vid2world/eval_inputs`. Runtime configs must use these role-based fully-qualified paths.

### LVDM fork status

- **T2V-Turbo** — Shared role-based components. Its VideoCrafter2 base resolves the common network, codec, encoder, and scheduler roles; the model keeps only its LoRA and consistency-sampling behavior.
- **VideoCrafter** — Shared role-based components. All packaged configs point directly to canonical role packages instead of a copied framework tree.
- **Dynamicrafter, MotionCtrl** — Shared role-based components. Existing synthesis adapters keep their product-specific behavior while importing the same LVDM components.
- **Vid2World** — Shared components plus explicit extensions. Its modified latent diffusion network, UNet, attention, DDIM sampler, and KV cache are named role components; datasets remain synthesis-owned.

### Guard rails

For every LVDM-derived integration:

1. Reuse canonical role components when checkpoint-visible structure is identical.
2. Add a narrowly named role component only when checkpoint or inference behavior differs.
3. Keep orchestration in a native recipe/pipeline and data adapters in synthesis.
4. Run `compileall`, target resolution, checkpoint key/shape checks when assets exist, and the relevant integration test subset.

Do not reintroduce a model-local `models/modules/pipeline/scheduler` framework hierarchy.
