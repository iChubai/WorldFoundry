# DualCamCtrl GPU validation

The in-tree DualCamCtrl runtime loaded the local 24 GB official control checkpoint together with Wan2.1 camera-control base, T5/VAE/tokenizer and CLIP components on GPU0. A 9-frame, 320×480, 8-step smoke with an RGB courtyard image, grayscale synthetic depth, and a small rightward synthetic camera trajectory produced [a decodable 10 FPS MP4](dualcamctrl-9f-8step.mp4). [Frames 0, 4, 8](contact.png) show the courtyard and walking woman remaining recognizable with coherent movement and no obvious scene collapse. See [status](status.json), [result](result.json), and [decode audit](decode.json). Peak allocated GPU memory was 24.1 GB. This validates local inference only; the official 61-frame/50-step recipe and quantitative camera/depth control were not tested.

The first attempt failed because the standard checkpoint-root environment was not set to the local `../ckpts` directory. The runtime now also resolves providerless local snapshot names (used by the CLIP checkpoint) and reports missing assets explicitly instead of raising a misleading all-weights-missing error. A second attempt exposed a validation-fixture serialization mistake: the synthetic camera file held a NumPy array that the safe weights-only loader rejects. The fixture now holds a tensor and is checked before heavy checkpoint loading. The final run completed.
